# Switch 移植（GT4 优先）

目标：把 ps2-web-recomp 为 Gran Turismo 4 生成的 C++ 编译成 Switch 自制程序（.nro），用你自己的光盘镜像在自己的机器上运行。生成的代码和游戏数据都属于游戏版权方，只能留在自己的设备上，不要发布。

## 架构：哪些能直接用，哪些要换

| 部分 | 代码 | Switch 上的情况 |
|---|---|---|
| EE 重编译器 `eerecomp`、`vurecomp` | `recomp/` | 在 PC 上运行，输出可移植的 C++，不用改 |
| 运行时：内核 HLE、IOP、DMAC、VIF、VU、SPU2、IPU、软件 GS | `runtime/` | 纯 C++20，已能用 GCC 编译，也能交叉编译成 AArch64 |
| 窗口、输入、音频 | `host/window.cpp`（SDL2） | 复用 devkitPro 的 switch-sdl2，已加 `__SWITCH__` 分支 |
| GPU 渲染器 | `runtime/src/gs/gpu/`（WebGPU + WGSL，约 3000 行） | 原样复用：`gpu/gl/` 用 OpenGL 4.3 实现了它用到的 WebGPU 函数，见第 2 阶段 |
| VU 即时编译 | `vu_jit*.cpp`（生成 WebAssembly） | 只有网页版用。Switch 用预编译的 VU 程序，没见过的程序走解释器 |

## 阶段

### 第 0 阶段：可移植性（已完成，在 `switch-port` 分支）
- `vu_ops.hpp` 里两个 clang 专用内建函数加了 GCC 回退（devkitA64 用的是 GCC）。clang 和 GCC、-O0 和 -O2 的结果逐位一致，新测试 `vu_ops_bits` 会持续检查这一点。
- 生成代码里的 `[[clang::musttail]]` 改成 `PS2_MUSTTAIL` 宏。clang 用 `clang::musttail`，GCC 15+ 用 `gnu::musttail`；更旧的编译器只在生成代码里报错，不会悄悄生成可能爆栈的程序。
- 运行时全部 27 个源文件都能交叉编译成 AArch64 目标文件。用的是借来的 x86 头文件，所以这只能说明代码里没有平台相关的写法，不等于在 Switch 上编译通过。
- 新增 `host/switch.cpp`（libnx 入口：从 SD 卡读启动参数，检查是否是应用模式，可选 CPU 超频和日志）、CMake 里的 `ps2nx` 目标、`scripts/build_switch.sh`。
- 所有合成测试在 clang 和 GCC 下都通过。

### 第 1 阶段：在 Switch 上启动 GT4
目标是验证正确性：能开机，进菜单，有声音，能读写存档。第 2 阶段做完后默认就走 GPU 渲染；如果画面有问题，可以在 `args.txt` 里加一行 `@env PS2_GS=cpu` 换成软件渲染对照（会非常慢：原作者在 PC 上用软件 GS 加 VU 解释器只有大约 3 FPS）。
- 要验证：线程栈（16 MiB）、内存（必须用应用模式启动）、光盘流式读取、手柄映射、音频节奏。
- 调试：在 `args.txt` 里加 `@log`，或者用 nxlink。

### 第 2 阶段：GPU 渲染器（已完成，待真机验证）
没有重写渲染器，而是让原来的渲染器在 OpenGL 上运行：
- `runtime/src/gs/gpu/gl/webgpu_gl.cpp` 用 OpenGL 4.3（EGL）实现了 `gpu.cpp` 用到的那组 WebGPU 函数。上游的 `gpu.cpp` 一行没改，以后同步上游几乎没有冲突。
- 着色器由 wgpu 内置的 naga 预先从 WGSL 翻译成 GLSL（`scripts/gen_glsl.py` 生成 `gl/shaders.cpp`）。WGSL 改了之后重新运行它；`gl_shaders_current` 测试会在没同步时报错。
- 语义和 WebGPU 一致：命令先录制、提交时执行；缓冲区初始为零；每次 dispatch 之后加内存屏障；回读用 fence 异步完成。
- **验证结果：** 合成测试覆盖纹理上传、CLUT、各种图元、混合、深度和 Alpha 测试、纹理过滤、本地拷贝和渲染到纹理。在 1、2、3 倍内部分辨率下各跑 100 到 200 个场景，OpenGL 版的 GS 显存和显示输出与原版 WebGPU（Vulkan）**逐字节一致**，clang 和 GCC 编译的结果也一样。复查命令：`scripts/compare_gpu_backends.sh`。
- Switch 上由 OpenGL 后端直接画到主机的原生窗口（NWindow），不经过 SDL 的渲染器；GPU 初始化失败时自动退回 SDL 软件显示（也可以在 `args.txt` 里写 `@env PS2_SDL_RENDERER=1` 强制）。
- 构建：Switch 默认使用这个后端（CMake 选项 `PS2_GPU_BACKEND=gl`，链接 `EGL glapi drm_nouveau`）。只需要 WebGPU 的头文件，不需要 wgpu-native 库本身。
- **还没验证的：** 真机上 nouveau 驱动的着色器编译和速度、显示路径（这边没有窗口系统，测不了画到屏幕这一步）、HOME 菜单的挂起和恢复。

### 第 3 阶段：性能（进行中）
第一次真机测试（CPU 1963 MHz、GPU 998 MHz、内存 2133 MHz）的结果：
- 菜单 20 到 30 帧，比赛 3 到 5 帧。超频插件显示 CPU 各核都没跑满，GPU 和内存带宽负载都在 90% 以上。
- 菜单里瓶颈是 GPU 渲染：日志显示 `gs` 线程空闲 0%，模拟线程有 88% 在等。
- 比赛里主要是 VU 程序没被预编译（`vu1 interpreted` 每秒 3000 次）：PC 上的探索运行没进过比赛，比赛用到的 VU 微程序没录下来。

对应的工具：
- **录制没见过的代码：** `scripts/build_switch.sh gt4 --record --log` 打包的版本会在 SD 卡上记下没预编译的 VU 程序（`vu1/`）和没翻译到的 EE 代码地址（`misses.txt`）。玩一圈之后，`scripts/import_switch_run.sh gt4 <镜像> <卡上的 switch/ps2recomp 文件夹>` 会把它们导回来、重新翻译编译、重新打包。多录几次，覆盖不同的赛道和车辆。
- **GPU 时间分析：** `--stats` 让 `log.txt` 每秒多一行 `[gl]`，列出渲染线程花在发命令、上传、等待、回读和显示上的时间，以及 GPU 在每个着色器入口上花的时间。
- OpenGL 层现在只重新绑定发生变化的缓冲区，合成测试里省掉了约 88% 的绑定调用，输出仍与 WebGPU 逐字节一致。
- 之后：根据 `[gl]` 的数据优化最耗时的着色器。线程绑核和降低内部分辨率也在候选里，不过默认已经是 1 倍。

### 第 3b 阶段：原生光栅化渲染器（方案 B，第一版已完成，待真机验证）
依据（都是真机数据，CPU 1963 MHz）：
- 现有的计算着色器渲染器：Mesa 26 的 nvc0 比 Mesa 20.1 快约 2.2 倍，比赛仍只有 5 到 8 帧，GPU 占满。zink（Vulkan）更慢。
- NetherSX2_nx（PCSX2 系，原生三角形光栅化）跑同一个游戏约 28 帧，GPU 在 768 MHz 下负载只有 22% 到 27%，一个 CPU 核跑满。说明这块 GPU 用原生光栅化画 GT4 绰绰有余，它卡在 CPU。
- 我们的模拟线程在比赛里每帧约 20 ms，所以配上够快的渲染器，上限在 50 帧左右。

设计：
- GS 显存仍是一块 GPU 缓冲区，纹理直接在片段着色器里从这块缓冲区取（沿用现有的地址换算和 CLUT 代码），所以不需要纹理缓存。
- 正在绘制的帧缓冲和深度缓冲用真正的 GPU 纹理（按 FBP、FBW、格式缓存）。有人要读对应的显存区域时（当纹理采样、本地拷贝、回读、显示），再把纹理写回显存缓冲区；显存被别的途径改写后，下次绘制前从显存重新载入。
- 混合、深度测试、Alpha 测试尽量映射到 GPU 的固定功能。映射不了的状态整批退回现有的计算着色器光栅化，所以任何时候画面都应当是对的，只是那一批慢。
- 分步扩大原生路径覆盖的状态。先做哪些由 `--census` 的统计决定：它每十秒列出游戏用到的绘制状态和各自覆盖的屏幕面积。
- 桌面上仍走 WebGPU，Switch 上走 `gl/` 那层，两边共用同一套 WGSL，继续用合成场景和计算着色器版本对照（原生光栅化不可能逐位一致，按容差比较）。

#### GT4 比赛的绘制状态统计（真机，88 个十秒窗口）
每帧约 250 批、2 万个图元；其中约 65 批会把自己正在画的目标当纹理读（全屏后处理）。包围盒面积合计约 38 个屏幕。按面积排序的主要状态：

| 面积 | 图元 | 状态 |
|---|---|---|
| 约 43% | 约 55% | 三角形，目标 CT32，深度 Z24 `>=` 并写入，Alpha 测试 `>` 失败丢弃，纹理 T8/T4（CLUT）modulate、双线性、雾、Gouraud。这是赛道和车身 |
| 约 15% | 约 6% | 同上但带混合 `(Cs-Cd)*As+Cd`，不写深度，多数带帧缓冲通道掩码 |
| 约 7% | 很少 | 不带纹理的三角形，深度 `>=`，Alpha 测试 `>` |
| 约 25% | 很少 | 全屏精灵：清屏、清深度（Alpha 测试 never、失败只写 Z）、常量混合 `Cd*FIX`、`Cs*FIX+Cd`、`(Cs-Cd)*FIX+Cd`、`Cs*Ad+Cd`，以及读 CT32 目标的后处理 |
| 约 1% | 约 7% | 目标 Alpha 测试（DATE）加 `Cs*Ad+Cd` |
| 约 1% | 约 1% | Alpha 测试失败只写 RGB，再加混合 |

要点：
- 颜色目标几乎只有 CT32（少量 CT24，一处把 Z24 当颜色画），深度只有 Z24。
- 出现的混合公式只有五种，都能映射到固定功能混合（PS2 的 Alpha 0x80 等于 1.0，着色器里要乘 2）。
- 第一版原生路径的范围：CT32/CT24 目标，Z24 深度的各种测试，Alpha 测试失败丢弃，这五种混合，按字节的通道掩码，纹理从显存缓冲区直接取。DATE、失败只写 RGB、把 Z 当颜色画先退回计算着色器。
- 每帧 65 次"读自己的目标"是性能关键：不能每次都把整个目标写回显存，需要让 CT32 的目标纹理可以直接被采样。

#### 第一版原生路径（已完成，待真机验证）
代码在 `runtime/src/gs/gpu/native.wgsl`（着色器）、`gpu.cpp`（`native_state`、`flush_native`、目标纹理的写回和载入）和 `gl/webgpu_gl.cpp`（OpenGL 上的纹理、帧缓冲和渲染管线）。Switch 上默认开启，桌面上用 `PS2_GPU_NATIVE=1` 打开。

- **走原生路径的绘制：** 三角形和精灵；目标 CT32 或 CT24；深度 Z24、Z32、Z16、Z16S 的各种测试和写入（深度值不超过 24 位的图元；Z32 缓冲区里超过 24 位的旧值原样留在显存里）；Alpha 测试失败丢弃（以及测试恒不通过的清屏、清深度写法）；按整字节的通道掩码；系数为源 Alpha 或 FIX 的混合（上表五种里的四种）；纹理从显存缓冲区直接取。
- **整批退回计算着色器的：** DATE、Alpha 测试失败只写一部分、系数为目标 Alpha 的混合（`Cs*Ad+Cd`）、通道内部的掩码、PABE、不钳位的颜色、深度值超过 24 位的图元、16 位目标、线和点、顶点 Alpha 超过 0x80 的混合。两条路径之间靠显存缓冲区交接：别的途径要读写某块显存前，盖在上面的目标纹理先写回；显存被改写后，目标纹理在下次绘制前重新载入。
- **像素怎么算：** GPU 的光栅化只决定哪些像素可能被覆盖（三角形每条边向外扩 1/8 像素），每个像素的颜色、纹理坐标和深度仍用计算着色器那套算式在片段着色器里算，所以不带混合时两条路径的结果逐位相同，可以在同一帧里交替绘制而不会出现深度打架。混合交给固定功能：GS 是截断，GPU 是四舍五入，每次混合最多差一级。
- **已知的近似：** 混合系数含纹理 Alpha 时，假定纹理 Alpha 不超过 0x80（即 1.0），超过的按 0x80 算。游戏的纹理一般满足；如果某处半透明明显不对，在 `args.txt` 里加 `@env PS2_NATIVE_SKIP=128` 让这类绘制退回计算着色器来确认。
- **验证结果（`scripts/compare_native.sh`，1、2、3 倍内部分辨率各 100 个场景，WebGPU 和 OpenGL 两个后端）：** 不带混合时，原生路径与计算着色器的显存和显示输出逐字节一致（普通场景和按上表状态分布生成的"比赛"场景都是）；带混合时所有字节相差不超过 8（单次混合差 1，经过纹理函数和多层混合会放大），3 倍分辨率下每 100 个场景有 4 个字节超出。OpenGL 与 WebGPU 的计算着色器输出仍逐字节一致（`scripts/compare_gpu_backends.sh`）。
- **还没验证的：** 这边只有软件光栅化（llvmpipe），真机 nouveau 驱动上的正确性和速度都要实测。原生路径需要 `glClipControl`、双源混合，以及顶点和片段着色器里能用存储缓冲区；缺任何一项会在日志里写明并自动全部退回计算着色器。
- **还没做的（下一步）：** 每帧约 65 次"读自己的目标"现在每次都把目标的脏区写回显存，再从显存取样。这是正确的，但很可能是下一个瓶颈，要让 CT32 目标纹理能被直接采样。其次是 DATE 和 `Cs*Ad+Cd`（各约 1% 面积）。

真机上怎么看效果：
- `scripts/build_switch.sh gt4 --stats` 打包后，`log.txt` 每秒多一行 `[native]`：两条路径各画了多少批、多少图元，以及目标纹理写回（stores）和载入（loads）的次数。比赛里理想情况是绝大多数图元在 native 一侧；stores 和 loads 每帧几十次以上就说明交接是瓶颈。后面还有两行：`compute because` 按原因列出没走原生路径的图元数和批数（每秒），`stores for` 按用途列出写回次数。
- 画面不对时，在 `args.txt` 里逐个试：`@env PS2_GPU_NATIVE=0`（完全关掉，确认问题出在原生路径）、`@env PS2_NATIVE_SKIP=<数字>`（把某一类绘制留给计算着色器：1 带系数的混合，2 所有混合，4 带纹理，8 Alpha 测试，16 深度测试，32 三角形，64 精灵，128 系数含纹理 Alpha 的混合；可以相加）、`@env PS2_NATIVE_SYNC=3`（每批前后都同步目标和显存，很慢，用来判断是不是交接出错）。
- `@env PS2_NATIVE_Z=fast` 用 GPU 自己插值的深度，被遮住的像素可以提前丢弃，更快，但深度可能与计算着色器差一级，两条路径画的面贴在一起时可能闪烁。

#### 真机第一轮结果（Mesa 26，带 `--stats`）
- 比赛平均 10.6 到 11.3 帧。每帧约 1.1 万个图元走原生路径，约 5000 个图元、160 批仍走计算着色器，写回约 65 次。
- 留在计算着色器的原因（每帧图元数/批数）：深度缓冲区不是 Z24 约 3940/141，DATE 约 870/11，`Cs*Ad+Cd` 约 132/4，16 位目标约 21/2。之前的面积统计没显出第一项，因为这些图元面积很小。
- 据此原生路径已放开到 Z32、Z16、Z16S。帧率没变（约 10.5 帧）：瓶颈转到两条路径的交接上，每帧写回约 155 次。
- 逐帧跟踪（`[trace]`）显示的一帧：约 2 万个图元、800 次绘制调用、1362 次 CLUT 载入、142 次上传。写回的最大来源是 GT4 的色彩校正：每帧 70 次，每次先往 `3DA0` 处一块 64x32 的目标画 48 个图元生成调色板，载入成 CLUT，再用它把 64x32 的一块画面画到 `0/10/CT24`（就是主场景深度缓冲区所在的显存）。这 70 批的深度设置是"恒通过、不写"，但深度缓冲区指向与帧相同的显存，原生路径因此放弃，每次还要重新载入一遍深度。现在这种深度设置直接当作不用深度。
- 改完后那 70 批走了原生路径，但帧率仍是 10.3：色彩校正每块要"画一块画面 → 把它当纹理读来生成调色板 → 载入成 CLUT"，原生路径下每块两次写回，写回反而涨到每帧约 200 次。对比几份日志估算，一次写回约占 0.2 ms 的驱动 CPU 时间（发 GL 命令每秒占到约 630 ms），写回次数就是现在的瓶颈。于是加了一条规则：包围盒不超过 4096 像素、且目标在显存里是最新的小批，直接交给计算着色器（`PS2_NATIVE_SMALL=<像素数>` 可调，0 关闭）。
- 这条规则生效后比赛约 13 到 16 帧，驱动里的 CPU 时间降到每秒约 130 到 180 ms，瓶颈回到 GPU（每帧约 36 ms）：计算着色器光栅化约 17 ms（主要是色彩校正的 140 批），原生渲染约 7 ms，纹理解码约 5 ms，CLUT 载入约 4 ms。`PS2_NATIVE_Z=fast` 在真机上车身和远景闪烁，而原生渲染本来只占约 7 ms，不采用。
- **色彩校正改为查表（`lut_try`，`PS2_GT4_LUT=0` 关闭）。** 把色彩校正前几批的图元完整记下来后确认：它对每个像素的红、绿、蓝各查一张 256 项的表，Alpha 不动。游戏的做法是每个 64x32 小块（帧的一页）两步：48 个精灵把这一页当 8 位纹理、以这张表为 CLUT 读到一块暂存页（红 16 个，蓝、绿各 16 个叠加）；再用 8 个精灵、8 张取自暂存页的 CLUT 和一张"计数"纹理把暂存页按原来的像素顺序写回。渲染器现在按硬件上记到的样子逐项核对这两步（状态、坐标、纹理坐标、CLUT 来源、计数纹理的内容），对上了就不画，把涉及的页攒起来，等别的操作到来时用一次计算调度完成查表，并把暂存页写成游戏最后一步留下的样子。`tests/gs_gt4_lut_test.cpp` 用软件渲染器把真实的绘制序列画一遍，确认它等于查表；再确认 GPU 渲染器无论开不开这条捷径、被别的操作打断与否，整块显存都与软件渲染器逐字节一致。
- 查表在真机上生效（每帧 70 块合成一次处理，GPU 上约 0.1 ms），比赛约 14 帧。GPU 仍是每帧约 40 ms：计算着色器光栅化约 13 ms（每帧约 30 批：小目标上的小批和 DATE），原生渲染约 10 ms，纹理解码约 7.5 ms（每帧约 350 次调度、450 万个纹素，逐批重解），CLUT 载入约 5 ms，上传约 3 ms，写回约 2.5 ms。GS 线程每帧约 70 ms 里，等 GPU 约 26 ms，发 GL 命令约 9 ms，写缓冲区约 5 ms（有时到 10 ms），其余约 29 ms 是渲染器自己的 CPU 工作，分布未知。
- 针对这几项：每次提交前整块重写的两个缓冲区改为先向驱动要新存储再写（`PS2_GL_ORPHAN=0` 关闭），避免等 GPU 用完旧的；排队的上传尽量提到 CLUT 载入之前，减少两类操作交替造成的调度次数；`[native]` 多一行 GS 线程在渲染器各部分的耗时。
- GS 线程计时的结果：渲染器自己的 CPU 工作每秒只有约 100 ms（`draw` 约 58 ms），其余约 790 ms 都在提交里，其中等画面交换约 460 ms、写缓冲区约 115 ms（改成要新存储后没变）、发 GL 命令约 124 ms。GPU 每帧约 40 ms，而一帧是约 71 ms：`eglSwapBuffers` 等到 GPU 画完这一帧才返回，之后 CPU 准备下一帧的约 30 ms 里 GPU 是空闲的，两者没有重叠。
- 因此改成延后交换（`PS2_GL_LATE_SWAP=0` 关闭）：呈现时只 `glFlush` 让 GPU 开始画，等到下一批命令要发出时才 `eglSwapBuffers`，让 GPU 画这一帧和 CPU 准备下一帧同时进行。
- 主场景（帧 `1A40`、深度 `0`）里剩下的交接：约 19 批车身反射（DATE 加 `Cs*Ad+Cd`，纹理 `2BC0`），每批前后各一次写回和载入；两块 64 像素宽的目标（`3500`、`3600`）用了隔行掩码。下一步是这两类。

### 第 4 阶段：体验
- ZL/ZR 只有开和关，要映射成满压力的 L2/R2（GT4 用压力键控制油门和刹车）。
- 掌机和底座模式的分辨率、HOME 菜单挂起和恢复、存档备份。

## 怎么构建

1. **在电脑上生成代码**（Linux、WSL2 或 macOS；需要 clang、CMake、Ninja、Python 3）：
   ```bash
   git checkout switch-port
   scripts/port.sh gt4 "Gran Turismo 4.iso" --native-only
   ```
   先在电脑上用 `build/native-gt4/ps2run ... --window` 确认能玩，再上 Switch。原生窗口需要 SDL2 开发包。
2. **装 devkitPro**：`dkp-pacman -S switch-dev switch-sdl2 switch-mesa`。devkitA64 的 GCC 必须是 15 以上（`aarch64-none-elf-gcc --version`）。
3. **构建 Switch 版**：
   ```bash
   scripts/build_switch.sh gt4 --log
   ```
   然后把 `build/switch-gt4/sd/` 里的内容复制到 SD 卡根目录，再把光盘镜像复制成 `switch/ps2recomp/gt4.iso`。GT4 是双层 DVD，镜像超过 4 GiB，SD 卡要用 exFAT 格式。
4. **启动**：在任意游戏上按住 R 进入自制程序菜单（应用模式），再打开 ps2recomp。从相册进入的话内存不够。

## 已知风险
- 这一阶段的 Switch 代码还没有用真正的 devkitPro 编译过，这边没有 libnx 和 switch-sdl2。第一次编译时可能要修几处小问题。
- GCC 15 的 `musttail` 在 AArch64 上对生成代码的函数签名是否都能满足，要到第一次构建时才知道。不满足的话，换成 clang 加 devkitPro 的 sysroot 来编译。
- 原作者用的是 GT4 PAL 版；其他版本在电脑上跑通了再上 Switch。
